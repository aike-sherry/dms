# 命名体系收敛决策对比（R39 后续·业主拍板用）

> 现状：系统里并存**两套文件命名逻辑**——旧体系（PM 的「命名规则」模板 + 智能命名/纠错 + 归档路由）与 R39 新体系（admin 骨架库 + 目录绑定 + CRA 确认向导 + 双名审计）。本文盘点真实触达面、对照差异、给出收敛方案建议。**结论先行：推荐方案 C「渐进收敛」。**

## 一、两套逻辑各自触达面（按代码实测，精确到角色→页面→入口→调用链）

### 旧体系：命名规则 + 智能处理 + 归档路由

| 角色 | 页面 | 入口 | 实际调用链 |
|---|---|---|---|
| PM | TRANSFER | 工具栏「命名规则」 | `NamingRuleDialog` → 编辑全局唯一模板 `state.namingTemplate`（持久化，全系统生效） |
| PM | TRANSFER | 「上传」 | `UploadDialog`（PM 模式）→ `autoNameBatch` 按上面模板渲染，**落库即定名、无确认** |
| PM | STUDY/SITE TMF 钻取 | 「上传」 | `TmfUploadDialog` → `applyNamingTemplate(state.namingTemplate)` 直接归档定名，**无确认** |
| PM | TRANSFER | 文件行「智能命名 / 智能纠错」 | `SmartProcessDialog` → `suggestName / findIssues / applyFixes` → `renameFile` 直接改写文件名，**无审计日志** |
| CRA | TRANSFER | 文件行「智能命名 / 智能纠错」 | 同上（`ExTransfer` 挂同一弹窗） |
| CRA | TRANSFER | 「上传」确认命名 | **目标目录未绑骨架时**：仍按旧模板预览（`applyNamingTemplate`），逐行确认后落库，**无审计** |
| PM | TRANSFER「归档」/ REVIEW「通过」/ PdfPreview「归档」 | 归档动作 | `archiveRouter.planArchive`：`analyzeName` 从文件名猜类型 → 查 `state.archiveRoutes` 路由表 → 落入 STUDY TMF「分区/类型」文件夹；猜不出进「99 待分拣」（工具栏「待分拣」人工归位） |
| PM | TRANSFER | 工具栏「归档规则」 | 维护路由表 `state.archiveRoutes`（文档类型→分区） |

### 新体系：R39 模式A（骨架 + 绑定 + 向导 + 审计）

| 角色 | 页面 | 入口 | 实际调用链 |
|---|---|---|---|
| admin | NAMING | 整页 | `AdminNaming`：骨架库 / 文档类型字典 / 目录树模板库 / AI 预填开关 |
| PM | STUDY/SITE TMF 钻取 | 文件夹行「绑定骨架」 | `setFolderTemplate` 绑定；`effectiveTemplateRef` 沿目录链继承 |
| CRA | TRANSFER | 「上传」确认命名 | **目标目录已绑骨架时**：行内展开向导（`renderSkeleton` 实时预览、类型/版本/状态下拉、可手动覆盖）→ 确认才落库，写 `originalFilename`（永不可改）+ `displayFilename` + 业务字段 + **审计日志**；重名自动追加（2）（3）并记「重名追加」 |
| PM | STUDY/SITE TMF 钻取 | 文件行「属性」 | 改展示名 → `renameDisplayFilename` + 「修改文件名」审计；命名历史时间线 |
| admin | AUDIT | 整页 | `AdminAudit`：全局命名流水（创建命名/修改文件名/重名追加） |

**共用底层**：`smartDoc.ts` 的 `analyzeName`（文件名识别）与版本链函数同时被两套使用——旧体系的归档路由、智能命名，新体系的 AI 预填、未绑定行预览、版本历史（`VersionHist`）都靠它。这是收敛时**不能一刀删**的关键。

## 二、功能重叠与差异对照

| 维度 | 旧：PM 上传自动命名 | 旧：智能命名/纠错 | 旧：归档路由 | 旧：CRA 未绑定行 | 新：骨架向导（绑定行） |
|---|---|---|---|---|---|
| 触发角色 | PM | PM + CRA | PM（归档/审核） | CRA | CRA |
| 触发点 | TRANSFER/TMF 上传 | TRANSFER 行操作 | 归档·审核通过 | 上传确认命名 | 上传确认命名 |
| 命名依据 | 全局单模板 + 文件名识别 | 18 类词典识别 | 文件名识别 → 路由表 | 全局单模板 | 目录绑定骨架 + 业务字段下拉 |
| 确认制 | ✗ 落库即定 | 弹窗确认 | ✗ | ✓ 逐行确认 | ✓ 可覆盖、始终确认 |
| 审计日志 | ✗ | ✗（直接改名无痕） | ✗ | ✗ | ✓ 全量（创建/改名/重名追加） |
| 批量支持 | ✓ 批内版本递增 | ✗ 单文件 | ✓ | ✓ | ✓ +「应用到全部」 |
| 重名处理 | 追加序号 | 追加序号 | — | 追加序号 | 追加序号 **且记审计** |
| 业务字段落库 | 仅文件名 | 仅文件名 | 仅落位 | 仅文件名 | 类型/版本/状态独立字段 |
| 配置入口 | PM「命名规则」 | 无（硬编码词典） | PM「归档规则」 | 同左 | admin NAMING |

## 三、并存的风险

1. **合规口径不一**：同一个 CRA 上传弹窗里，绑定目录的文件有审计、未绑定的没有——GCP 溯源要求下这是硬伤。
2. **文件名可被"二次无痕改写"**：CRA 确认落库后，PM/CRA 仍可用「智能命名」直接改写文件名（`renameFile` 无日志），与 `displayFilename` 双名字段的语义打架，审计链断点。
3. **两份类型词表**：旧词典 18 类（硬编码）vs 新字典 10 类（admin 可配），同一文件两处识别结果可能不同。
4. **配置分散、权责重叠**：PM 管「命名规则+归档规则」，admin 管「骨架+字典」，同一件事三个入口。
5. **数据语义分歧**：新体系落的 `docType` 业务字段**没有参与归档路由**——路由仍靠猜文件名，字段白落。
6. **维护成本**：双引擎并存；`analyzeName` 一改牵动四套功能，回归面大。

## 四、收敛方案对比

| | A 保留双轨 | B 旧体系退役、全切骨架 | **C 渐进收敛（推荐）** |
|---|---|---|---|
| 做法 | 明确分工：CRA 走新体系，PM 上传/归档沿用旧体系 | 骨架体系覆盖全部入口，删除旧模板/智能处理/路由表 | 先让 PM 归档环节也走骨架建议名+确认制；旧入口隐藏（数据代码保留）；观察后再删 |
| 用户体验 | 两个角色两套习惯，培训成本高但各自自洽 | 全系统一套逻辑，最统一 | 逐步统一，每步可回退 |
| 迁移内容 | 无 | ①存量目录全部补绑骨架 ②归档路由表→目录绑定映射 ③未绑定 CRA 行接骨架 ④删 smartDoc 大半/NamingRuleDialog/SmartProcessDialog/待分拣 | 分轮进行，见第五节 |
| 工作量粗估 | 0（但持续付双轨维护费） | 约 3–4 个开发轮次 + 全量回归，风险集中 | 每轮 0.5–1 天，独立验证，风险分散 |
| 主要风险 | 审计口径永久分裂；字段语义继续打架 | 一刀切：未绑定目录行为突变、PM 习惯被打断、归档路由依赖 `analyzeName` 的存量文件回归面广 | 观察期内仍短暂并存（可控） |
| 适用判断 | 仅当短期不打算推合规审计 | 仅当能接受一次大版本阵痛 | **常态选择** |

**推荐 C 的理由**：①审计合规不留断点——先堵住「PM 归档无确认无审计」这个最大缺口；②每轮独立验证、出问题可单轮回退，业务不停摆；③给「未绑定目录是否全量切骨架」留出真实使用数据再决定，避免 B 方案的一刀切风险；④A 只是把成本往后拖，口径分裂会随数据量放大。
